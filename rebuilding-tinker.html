Rebuilding Tinker

Tinker sells fine-tuning as an API where you keep the training loop and they keep the GPUs. The interesting part is not the API. It is the one constraint underneath it that turns a GPU rental business into a per-token one.

Researched 18 Nov 2026 · prices from the official Tinker docs

The one-sentence version

Fine-tuning a model normally means renting a cluster, wiring up distributed training, handling checkpoints, and recovering when a node dies at hour 14. That work is most of the effort and none of the thinking.

Tinker cuts the job along a different line. You write the training loop in Python on your own machine. When that loop needs actual GPU math, it makes a network call. Their cluster runs it and sends the result back.

It is deliberately not an upload-your-data-get-a-model button. Every decision that changes model quality stays with you. Every decision that is just plumbing goes to them.

The surface

Four verbs

The whole API is small enough to hold in your head. These primitives are enough to build any post-training algorithm: supervised fine-tuning, PPO, GRPO, DPO, distillation. 

# runs locally; each call is a network round trip
fwd = await client.forward_backward(batch, loss_fn="cross_entropy")
await client.optim_step(AdamParams(lr=1e-4))

# RL loops need to generate from the current policy, mid-training
out = await client.sample(prompt, num_samples=8)

# durable state, so a dead worker is not a dead run
await client.save_state(name="step-400")

Switching models is reported to be a one-string change. That only works because the client holds no model-specific code — it marshals data and awaits futures, and everything that knows about architecture lives server-side.

The mechanism

Why it can be sold by the token

Tinker only does LoRA, never full fine-tuning. Read as a feature list that is a limitation. Read as a business, it is the entire design.

A large base model is tens or hundreds of gigabytes and takes real time to load onto GPUs. A LoRA adapter is a few hundred megabytes at most. So you pay the expensive load once, keep the base weights resident, and swap cheap adapters per request. One pool of GPUs holding Qwen3.5-397B serves every customer fine-tuning that model, interleaved.

The pricing model is a claim about utilization. Charging per token means you have promised to eat every idle GPU-second. That is a better product and a worse risk, and it is only solvent if demand for each base model is dense enough to keep its pool busy.

Engineering

What is actually hard

The API is a weekend. These are the parts that take a team.

Keeping every pool warm

Tinker lists roughly twenty base models. Each needs its own resident pool, and a pool with one active customer loses money. You either concentrate demand onto few models or eat cold starts on the long tail.

Durable sessions

A fine-tuning run is a long stateful sequence, not a request. The adapter weights and the optimizer moments have to survive a worker dying at step 3,000 and resume without the client noticing. That is the failure recovery the product is selling.

Sampling against weights you are still training

RL loops generate from the current policy, then train on what they generated. So an inference workload and a training workload share one set of live weights and interleave on the same device. This is substantially harder than either alone.

Metering you can bill from

Prefill, sampling and training are priced differently, so every request has to be counted by phase, per tenant, accurately enough to put on an invoice and defend when questioned.

Sanity check the economics before believing them. Qwen3.5-9B trains at $1.46 per million tokens. If a pooled GPU-hour costs you $2.50 all in, you need to push roughly 1.7M training tokens per GPU-hour just to break even on that model. Whether that is comfortable or impossible depends entirely on sequence length, batch shape and how well you interleave — this arithmetic sets the bar, it does not clear it.

Runara

How much of this do you already have

More than you would expect. The pieces that usually take longest — multi-cloud provisioning and per-token metering — are already in the codebase.

  • Eight-provider GPU provisioning have AWS, GCP, Azure, Lambda, RunPod, DigitalOcean, TPU, GKE. aws.ts · gcp.ts · tpuDeploy.ts · k8sDeploy.ts
  • Per-token metering have Billing mode, per-million quotes, cursor-based metering and billed-token accounting already ship. tokenBillingQuote · tokenMeterCursor
  • Model catalog have Per-model, per-provider deployment configs and hardware mappings. models.ts · modelAwsConfigs
  • Tenancy, keys, quotas have Hashed API keys, org scoping, roles, audit log. apiKeys.ts · lib/tenancy.ts
  • Training control plane gap Session create/attach, the four primitives as durable RPCs, futures.
  • Adapter lifecycle gap LoRA create, version, checkpoint, restore, garbage collect.
  • Pooled worker runtime gap Resident base weights with hot adapter swap, and a scheduler over per-model pools.
  • Client SDK gap The thin Python package that makes the whole thing feel local.

Two things that do not carry over

BYOC is incompatible with pooling. You cannot interleave several customers' adapters inside one customer's own cloud account. A Tinker-shaped product only exists in managed mode, so it is a second product line beside BYOC rather than a feature of it.

It inverts your inventory risk. Today a customer rents a deployment and carries the idle cost. Pooling moves that onto your balance sheet: you hold capacity and lose money when it is quiet. That is a financing decision as much as an engineering one.

If you build it

The order that de-risks it

The temptation is to build the pooled runtime first, because it is the interesting problem. It is also the one that can only be justified by demand you do not have yet.

  1. Single-tenant training jobs, billed by the hour

    Run a fine-tuning job on a dedicated instance using the provisioning you already have. No pooling, no multiplexing, no new economics. This reuses the provider integrations, the model catalog and the hourly metering almost unchanged, and it answers the only question that matters: does anyone want to train here at all.

  2. Put the Tinker-shaped API on top of it

    Same four primitives, same client ergonomics, but each session still owns its worker. The economics are ordinary and the developer experience is already the product. You learn the hard parts — durable sessions, adapter checkpointing, sampling against live weights — while the scheduling problem stays trivial.

  3. Pool exactly one model

    Pick whichever base model demand has concentrated on, and make a single warm pool for it. Measure real utilization for a month. Per-token pricing becomes defensible only once that number exists, and only for that model.

  4. Widen, slowly, by measured demand

    Each additional pooled model is a standing capacity bet. Add one when its queue justifies it, and keep the long tail on single-tenant workers where the customer carries the idle cost.

The honest summary: steps 1 and 2 are a few weeks of work against infrastructure you already own, and they are worth doing on their own merits. Step 3 is where this stops being a feature and becomes a different company, with inventory, utilization targets and a balance sheet to match.
